# DNA Company Network — локальное демо

Три вымышленные компании исполняют один заказ через **настоящий Workflow SDK**, проверяют условия через DNA и показывают продвижение в двух сменных оболочках интерфейса. Отдельный поиск сравнивает будущие коммерческие предложения, сохраняя условия уже принятого заказа.

Это исследовательское приложение внутри `examples/`. У компаний нет реальных клиентов, денег, устройств или банковских подключений. Процессы выполняются локально; финансовые и физические события моделируются. Runtime не вызывает LLM: поведение трёх компаний описано TypeScript workflow. Codex-агенты использовались для разработки примера, а не подменяют собой исполняющий runtime.

## Запуск

Нужен **Bun 1.4.2**. Корневой проект использует **TypeScript 7.0.2**; workspace примера фиксирует **`workflow` 4.8.5** своим [package.json](package.json) и общим [lockfile](../../bun.lock). Корневая установка включает зависимости этого workspace; ядро DNA по-прежнему не имеет runtime-зависимостей.

Из корня репозитория:

```sh
bun --version
# Ожидается 1.4.2.
bun install --frozen-lockfile
bun demo:network
```

`bun run demo:network` — равнозначная полная форма последней команды. Скрипт сначала запускает `workflow build`, затем локальный supervisor и сервер. Сборка создаёт handlers SDK и manifest в `.well-known/workflow/v1/`; сервер использует сгенерированные handlers, а не вызывает функции workflow как обычные функции.

Открыть [локальное демо](http://127.0.0.1:3117). Сервер слушает loopback `127.0.0.1`; порт по умолчанию — `3117`.

Для отдельного каталога состояния и другого порта:

```sh
PORT=3118 DNA_DEMO_DATA_DIR=/tmp/dna-network-example bun demo:network
```

По умолчанию состояние находится в `examples/company-network/.demo-data`: записи authority — в `sessions`, дополнительное состояние интерфейса/runtime — в `runtime`, состояние SDK — в `workflow`. Секрет локальных игровых ролей также создаётся в каталоге данных. Не добавлять эти runtime-файлы в публичный репозиторий. Для нового независимого эксперимента можно выбрать другой `DNA_DEMO_DATA_DIR`; существующие сеансы не требуется удалять.

Остановка — `Ctrl+C`. Повторный запуск с тем же каталогом данных предназначен для продолжения сохранённых процессов на той же версии программы. Он не равнозначен созданию нового договора.

## Что происходит в сделке

| Субъект | Роль | Процесс |
|---|---|---|
| **Вектор Фабрика** (`buyer`) | Покупатель | Аванс → ожидание монтажа → явная приёмка → ожидание активации |
| **Контур** (`supplier`) | Устройство и программное обеспечение | Полученный аванс → комплект → ожидание приёмки → активация |
| **Реле Сервис** (`installer`) | Монтажный партнёр | Комплект → проверка часов → резерв времени → установка → передача результата |

Во всех случаях принятый installed order стоит **EUR 3 000**, первый год SaaS — **EUR 1 800**, всего договорное вознаграждение — **EUR 4 800**. Аванс — **EUR 1 500**. Начальные деньги покупателя — EUR 10 000, поставщика — EUR 2 000; закупка комплекта — EUR 900; выплата за завершённый монтаж — EUR 600. В обычном сценарии доступны восемь часов монтажника, резервируется шесть.

Начать можно с обычной сделки. При её создании SDK запускает три процесса. В обычном сценарии процесс покупателя сам выполняет синтетический аванс после короткого ожидания. После установки пользователь явно нажимает **«Принять результат»**; затем процесс поставщика активирует подписку. Установка моделируется задержкой workflow, а не реальной физической работой.

Каждый новый сеанс — независимая симуляция с собственными начальными деньгами, комплектом и часами. Несколько сеансов не конкурируют за общий склад или календарь одной организации; для такого эксперимента нужен общий внешний authority.

Дополнительные сценарии:

- **Недостаточно монтажного ресурса:** доступны четыре часа при необходимых шести. Процесс останавливается на нехватке ресурса. «Добавить ресурс монтажа» выполняет отдельное синтетическое изменение authority, после которого процесс может продолжить работу.
- **Аванс не получен:** процесс покупателя не проводит его автоматически. Закупка ожидает фактическую запись поступления; пользователь может запросить оплату доступной кнопкой.
- **Потерян ответ после резервирования:** authority уже записала списание EUR 900 и резерв комплекта, но шаг получает `RetryableError`. При повторе тот же ключ операции находит существующее подтверждение; повторное списание не является допустимым способом продолжения.

Выставленный счёт не считается деньгами. Завершённый монтаж не считается приёмкой. Приёмка старой версии не разрешает активацию текущей. Уже выполненный резерв сохраняет статус выполнения после уменьшения остатков и свободных часов.

Демо **не выполняет окончательный платёж EUR 3 300 и помесячное обслуживание SaaS**. Отображаемый остаток — договорная сумма после предусмотренного аванса, а не подтверждение её оплаты. Активация здесь демонстрирует завершение операционной цепочки; она не означает полного расчёта по договору. Для календарной выручки, денежных обязательств и оборотного капитала есть отдельная [экономическая модель](../../docs/business-model/economics.md).

## Границы между моделью, runtime и полномочным исполнителем

| Слой | Файлы | Ответственность |
|---|---|---|
| DNA | [model.ts](model.ts) | Чистые проверки procurement, commissioning, activation; расчёты и зависимости |
| Процессы компаний | [workflows/companies.ts](workflows/companies.ts) | Порядок работы, ожидание внешнего события, сигнал другому процессу |
| Шаги | [workflows/steps.ts](workflows/steps.ts) | Чтение состояния, повторная проверка, обращение к authority, запись событий |
| Authority | [authority.ts](authority.ts) | Проверка роли, версии и области операции; изменение денег/ресурса; подтверждение и идемпотентность |
| Runtime adapter | [runtime-state.ts](runtime-state.ts), [server.ts](server.ts), [run.ts](run.ts) | SDK handlers, запуск процессов, HTTP, локальное состояние, supervisor |
| UI IR | [ui-ir.ts](ui-ir.ts) | Проверяемые данные представления без выбора оболочки/темы |
| Интерфейс | [public/index.html](public/index.html), [public/app.js](public/app.js), [public/style.css](public/style.css) | Отображение IR и передача пользовательского запроса серверу |

В workflow используются директивы **`"use workflow"`**; внешние взаимодействия вынесены в функции с **`"use step"`**. Ожидания и сигналы используют API установленного SDK: `sleep`, `createHook`, `resumeHook`; повтор шага — `RetryableError`. Это реальное подключение SDK, а не собственный цикл с похожими названиями.

DNA не отправляет деньги и не резервирует часы. Положительное решение относится к снимку. Перед исполнением authority снова проверяет собственное актуальное состояние, роль и `expectedVersion`; повтор операции сверяется по стабильному ключу и квитанции. `unknown`, `conflict` и `error` не превращаются в разрешение.

В данном примере все три игровые роли доступны одному посетителю локального UI. Capability связывает запрос с ролью и сеансом, но **не удостоверяет реальную компанию или её сотрудника**. Поле `enabled` в UI IR — подсказка отображению, а не полномочие. Изменение HTML или JSON в браузере не должно заменять серверную проверку.

## Один UI IR, разные оболочки

IR имеет идентификатор **`schema: "dna.ui", version: "0.1"`**. Он описывает субъектов, показатели, связи, действия, решения, события, договор и знания для инспектора. В его схеме отсутствуют `theme` и `shell`.

Текущие переключатели:

- **«Сеть»** показывает связи между субъектами.
- **«Рабочее место»** показывает те же данные в другой компоновке.
- Светлая и тёмная темы меняют оформление; выбор сохраняется в браузере.

`validateUiIR` не знает терминов buyer/supplier/installer: идентификаторы, роли и названия субъектов произвольны. Бизнес-функция `projectCompanyUI` отдельно отображает текущий пример трёх компаний в этот общий формат. Тест с четырьмя субъектами — школой, садом, библиотекой и метеостанцией — проверяет именно независимость схемы от данного бизнеса. Он не является доказательством, что любая будущая компоновка уже визуально протестирована с любым числом субъектов.

Схема отвергает висячие ссылки, повторяющиеся идентификаторы и неизвестные свойства. На основных показателях и в инспекторе видны неизвестные, конфликтующие и ошибочные значения. Происхождение — caller assertions из DNA; отображение provenance не аутентифицирует источник.

## Паспорт экземпляра

Раздел **«Изделие»** предназначен для отдельного паспорта конкретного экземпляра: его идентичности, версии, компонентов и связей с договором и подтверждениями. Паспорт — данные предметной области поверх общей модели; он не требует добавлять промышленное оборудование в универсальную схему UI.

[`passportFor(session)`](passport.ts) возвращает устойчивую идентичность экземпляра, serial, модель/ревизию, BOM/ревизию, плату и UID чипа. Сервер включает паспорт в `/api/state`. Привязки к заказу, объекту, принятому scope и сервису появляются только по совпадающим событиям и квитанциям authority; каждая сохраняет `receiptId`, ключ операции и версию.

Все изготовленные идентификаторы этого примера имеют префикс `DEMO-` и являются синтетическими. Связанный serial или chip ID не доказывает физическое владение, подлинность чипа, происхождение компонента, корректность монтажа или соответствие требованиям. Для таких выводов нужны отдельно реализованные источники, протоколы и проверки. История замены компонентов пока не реализована: будущая замена должна добавлять связь старого и нового компонентов, сохраняя предыдущую историю.

## Обратная связь меняет будущую модель, а не прошлый договор

После активации доступно **«Передать отзыв»**. В текущем сценарии покупатель сообщает: **«Нужен экспорт данных CSV»**. Отдельный [feedback workflow](workflows/feedback.ts) проверяет применимость обратной связи через [feedback.ts](feedback.ts) и записывает предложение для будущей версии.

Формирование предложения не реализует CSV export, не изменяет цену и не добавляет обязанность по разработке в существующий заказ. Это промежуточный результат рассмотрения: новая гипотеза о следующем предложении с обозначенным контекстом. Неполная обратная связь или несовпадение версии не должны молча становиться принятой задачей на изменение продукта.

## Поиск вариантов будущего предложения

[evolution.ts](evolution.ts) — **ограниченный перебор семи заранее заданных кандидатов**, каждый из которых проверяется обычной фабрикой публичного DNA. Он не меняет действующую сессию или договор.

Перебираются installed price EUR 2 800 / 3 000 / 3 200 и шесть / восемь часов; дополнительно дан контрпример с пятью часами. Условные участники имеют предел цены покупателя EUR 3 100, доступные восемь часов монтажника и EUR 2 000 начальных денег поставщика. Аванс будущего предложения — 50%; комплект стоит EUR 900, труд — EUR 50/h, поездка — EUR 100.

Формулы для одной будущей установки:

```text
installation_cost = hours × 50 + 100
installed_contribution = installed_price − 900 − installation_cost
remaining_buyer_value = buyer_price_cap − installed_price
```

Обязательные ограничения: не менее шести часов условного качественного выполнения; цена не выше заданного предела; достаточно часов; денежный остаток неотрицателен на каждом шаге заданной последовательности; прямой вклад положителен. Сначала выбираются допустимые кандидаты, затем максимизируется вклад поставщика, затем остаток условной ценности покупателя при равном вкладе.

| Будущая цена | Часы | Прямой вклад | Результат |
|---|---:|---:|---|
| EUR 2 800 | 6 | EUR 1 500 | Допустим |
| EUR 2 800 | 8 | EUR 1 400 | Допустим |
| **EUR 3 000** | **6** | **EUR 1 700** | **Лучший среди данного набора по выбранной цели** |
| EUR 3 000 | 8 | EUR 1 600 | Плановый baseline поиска |
| EUR 3 200 | 6 | EUR 1 900 | Цена выше заданного предела покупателя |
| EUR 3 200 | 8 | EUR 1 800 | Цена выше заданного предела покупателя |
| EUR 3 000 | 5 | EUR 1 750 | Нарушен минимальный объём качества |

Плановый baseline восемь часов — сравнение **новых предложений**. Он не переписывает EUR 600 принятых затрат монтажа текущего demo order. Модель установленного комплекта в поиске также не включает SaaS, CAC, fixed, гарантии, налоги и разработку.

Денежный порядок учитывает начальный остаток, полученный аванс, закупку, оплату труда/поездки и только затем финальный платёж. Дополнительный тест задаёт EUR 2 800, восемь часов, нулевые начальные деньги и аванс 20%. Прямой вклад остаётся **EUR 1 400**, но после закупки и монтажа cash достигает **−EUR 840**; кандидат отклоняется. Поздний финальный платёж не устраняет ранний дефицит.

Ограничения результата содержатся и в JSON: **`bounded synthetic search; no global optimum or real demand proof`**. Мы не измеряли willingness to pay, производительность монтажника или зависимость качества от часов. Порог шести часов задан как условие упражнения. Другая цель, например сначала максимум выгоды покупателя, может выбрать другой допустимый вариант.

## Следующий шаг: агент предлагает изменения TypeScript

Более сильный эксперимент можно построить вокруг проверяемого цикла:

```text
Гипотеза об изменении бизнеса
    → агент предлагает ограниченный TypeScript patch
    → контрпримеры и регрессионные проверки
    → оценка на зафиксированных сценариях и бюджете
    → review результатов, зависимостей и исключений
    → Git-изменение новой версии модели
```

Агенту можно поручить предложить новое правило цены, план ресурсов или перечень допустимых договорных условий. Проверки должны сохранять отрицательные сценарии, принятые договоры, неизвестные и конфликты. Нужны отдельные критерии бизнеса и качества модели: высокая маржа не оправдывает пропуск обязательного объёма работ или неплатёжеспособную последовательность.

Важно разделять поиск параметров фиксированной программы и поиск самой программы. Здесь реализован **только конечный поиск параметров**. Непрерывный агентный цикл, автоматическое редактирование TypeScript, автоматическое принятие патчей и бесшовная миграция исполняющихся процессов не реализованы. Артефакт предложения и успешная симуляция сами по себе не дают права менять действующий договор или внешнюю систему.

## Восстановление и практические ограничения

Используется **Local World установленного Workflow SDK** и файловое локальное состояние. Supervisor может перезапустить worker; step retry сверяет запись authority по тому же ключу. Пример предназначен для изучения повторов и продолжения работы в пределах одной локальной конфигурации.

Это **однопроцессный** полномочный исполнитель. Здесь нет распределённой транзакции между компаниями, межпроцессного блокирования общего каталога данных, производственной аутентификации или гарантии сохранности при потере питания. Atomic rename файла помогает не показывать частично записанный JSON, но не решает весь набор проблем долговечности. Записи SDK, domain authority и дополнительной истории интерфейса не являются одной общей атомарной транзакцией.

Replay относится к сохранённой истории и совместимой, здесь — той же — версии кода. После изменения workflow, формата записей или семантики шагов нельзя предполагать бесшовное продолжение старых запусков. Перед таким обновлением требуется отдельная стратегия версий/миграции; текущий пример её не реализует.

Сгенерированный workflow code и TypeScript проекта исполняются как доверенный код репозитория. Демо не является безопасной средой выполнения произвольных программ, предложенных внешним агентом.

## Проверки и статус верификации

Масштаб проверяется отдельным [экспериментом на тысячах компаний](../../docs/network-scale.md): `bun run scale:network`. Он использует связанную сеть с общими ресурсами и отдельный каталог данных. Массовая цепочка ограничена резервированием, предоплатой и аудитом участников; интерактивное демо по-прежнему показывает полный небольшой сценарий.

Из корня репозитория:

```sh
bun test tests/company-network-model.test.ts
bun test tests/company-network-authority.test.ts
bun test tests/company-network-ui-ir.test.ts
bun test tests/company-network-feedback.test.ts
bun test tests/company-network-evolution.test.ts
bun run verify
bun run verify:network
```

Покрываются чистые решения DNA, ограничения полномочного исполнителя, обработка повторов, независимость UI IR, обратная связь и перебор кандидатов. Это отдельные виды проверки; зелёные unit tests не означают успешного сквозного выполнения в браузере или доказательства производственной надёжности.

Скрипт `verify:network` собирает настоящий SDK, запускает отдельный supervisor с временным каталогом, воспроизводит потерю ответа и перезапуск, проверяет сохранение run IDs, деньги и receipts, ограничения ролей, нехватку часов, ожидание аванса, паспорт, feedback и восстановление сохранённого запроса, ещё не переданного в SDK. Он завершает дочерние процессы и удаляет только созданные им временные данные.

Для уже запущенного демо есть [проверка браузера](../../scripts/company-network-browser.mjs): `node scripts/company-network-browser.mjs`. Она требует отдельно доступного Playwright и Chrome; `DNA_PLAYWRIGHT_MODULE` задаёт путь к Playwright, если он установлен вне репозитория. Скрипт создаёт два вымышленных сеанса через UI, воспроизводит запоздалый ответ предыдущего сеанса, завершает приёмку и feedback, проверяет паспорт, семь кандидатов, обе оболочки/темы и мобильную ширину 390 px. Снимки по умолчанию сохраняются в `/tmp/dna-network-browser`; `DNA_BROWSER_OUTPUT=none` отключает их. Playwright не добавлен в зависимости ядра или runtime демо.

Публичный `/.well-known/dna` отдаёт экспериментальный discovery DNA с проверяемым `/api/contracts`. Отдельный `/api/interface` описывает HTTP-поверхности демонстрации; `/api/ui`, `/api/model` и `/api/evolution` позволяют изучить данные интерфейса, граф и поиск предложений. Эти маршруты не объявлены универсальным или зарегистрированным стандартом.
