# Бизнес-директивы, Saturn и durable execution

Дата исследования: 2026-09-05. Статус: предложение архитектуры и план сравнительного эксперимента; новые директивы, compiler и durable adapter в DNA не реализованы.

**Рекомендация: декомпозировать систему по трём режимам — решение, процесс и внешняя операция. Предметные роли «сведения», «обязательство», «представление» описывать типизированными данными.** Директива заслуживает отдельного имени, когда за ней стоят отличающиеся правила выполнения, проверяемые ограничения и исполнитель. Имя бизнес-сущности само по себе такого режима не создаёт.

Для начальной интеграции достаточно обычных функций DNA, существующих `use workflow` / `use step` Workflow SDK и явных контрактов адаптеров. Возможный `use decision` — отдельная исследовательская гипотеза об удобстве authoring. Решение о compiler зависит от сравнения с текущим API, а не предшествует ему.

## 1. Что действительно делают WDK и Saturn

Указанная пользователем ссылка `worklfow-sdk.dev` не открылась. В официальном репозитории найден адрес [workflow-sdk.dev](https://workflow-sdk.dev). Исследованы официальные страницы и локальный checkout Workflow, HEAD `56ba32fe`. Документация изменяется; перед реализацией необходимы выбранные версии SDK и backend, проверка совместимости с toolchain DNA и реальные failure tests.

WDK сохраняет результаты шагов в журнале, переигрывает orchestration и возобновляет ожидания. `use workflow` и `use step` задают разные execution contexts; compiler заменяет вызовы шагов proxy и собирает различные bundles. **Сохранённый результат не делает произвольный внешний эффект идемпотентным.** Если платёж принят, а ответ потерян, повтор должен использовать согласованный ключ дедупликации. Документация отдельно различает step retries и повторный запуск всего workflow. Активный hook token также не является бессрочным реестром уже исполненных бизнес-операций. [Workflows and Steps](https://workflow-sdk.dev/docs/foundations/workflows-and-steps), [Idempotency](https://workflow-sdk.dev/docs/foundations/idempotency).

Обычная memoization связывает результат с аргументами чистой функции. Durable execution дополнительно связывает его с конкретным invocation, историей и версией выполнения. Два заказа с одинаковыми суммами не должны схлопнуться в одну оплату; два повтора одного платежа не должны создать две оплаты.

В Saturn исследовано текущее рабочее дерево, базовый HEAD `bb36d51`, с незакоммиченными изменениями. Выводы относятся к прочитанным файлам, а не к утверждению, что один этот commit содержит всю реализацию. Изучены профиль языка, compiler, metadata extraction, reference runtime и негативные тесты. Saturn не изменялся; его проверки в этой сессии не запускались.

| Механизм Saturn | Фактическое наблюдение | Вывод для DNA |
|---|---|---|
| Три директивы | `use control`, `use protection`, `use sequence`; проверяются место директивы и sync/async | Классифицировать режим выполнения, а не каждое бизнес-понятие |
| Semantic compiler | TypeScript Program/TypeChecker, lowering в IR, ограничения AST/effects, ошибка блокирует IR | Простота исходника оплачена сложностью compiler и проверок |
| Effect/ownership checks | Ограничены команды из pure helper и конкурирующие normal owners | Выделить право читать, предлагать и совершать изменение |
| Metadata extraction | Декларации оборудования и связи собираются без выполнения module/constructor/callback | Предметные объявления и исполняемая логика — разные слои |
| Capability profile | Reference IR явно отличается от deployment artifact | Адаптер должен сообщать проверенные возможности, без выводов из красивого имени |
| Runtime limitations | Single-scan runtime отклоняет sequence; protection dominance явно отсутствует | Директива и IR не доказывают наличие заявленной runtime-гарантии |
| Short-circuit | IR сохраняет условное чтение правой части JS-оператора | Для DNA отдельно нужна семантика unknown/conflict, обычной truthiness недостаточно |

В Workflow: `packages/swc-plugin-workflow/spec.md`, разделы Step Mode, Workflow Mode, Closure Variables. Реальные клиентские примеры из Saturn не перенесены.

## 2. Две независимые оси декомпозиции

**Предметная роль** объясняет, что означает объект:

- Сведение: кто что сообщил о конкретном объекте, периоде и контексте. Assumption/observation остаются различимыми метками происхождения; они не удостоверяют источник.
- Обязательство: какие условия приняты для конкретного scope и срока, кто вправе их изменить. Подтверждение принятия может отсутствовать или конфликтовать.
- Представление: какую часть сведений, обязательств и решений получает конкретный потребитель.

**Режим исполнения** объясняет, как работает функция:

| Режим | Вход и выход | Кто исполняет | Обязательная граница |
|---|---|---|---|
| Решение | Версионированный snapshot → значение/verdict + основания | Чистый evaluator DNA | Объявленные входы; unknown/conflict/error сохранены; сеть, время и запись не скрыты в callback |
| Процесс | Бизнес-идентичность + события → следующие ожидания/шаги | Durable runtime | История, версии, deadlines, повтор, отмена и handoff определены |
| Внешняя операция | Command intent + текущий контекст полномочий → receipt/rejection/unresolved outcome | Система, владеющая изменяемым ресурсом | Актуальная проверка, дедупликация, проверка версии и результат commit |

Чтение внешних источников тоже выполняется в IO-адаптере, обычно durable step с read-only capability; оно возвращает новый snapshot. Его не нужно выдавать за изменяющую бизнес-операцию. Политика допустимых эффектов конкретного адаптера задаётся явно.

Процесс покупки может содержать десятки вычислений цены, но они остаются обычными функциями внутри режима решения. Приобретение устройства и освобождение escrow различаются предметной логикой и authority; им не нужны независимые языки control flow.

## 3. Какие директивы заслуживают эксперимента

Ниже — кандидаты, не существующий API DNA.

| Кандидат | Какую повторяющуюся работу мог бы убрать | Что должен реально обеспечить | Приоритет |
|---|---|---|---|
| `use decision` | Ручную регистрацию вычисления, привязку входов, трассировку объяснений | Детерминированность в поддержанном профиле, dependency contract, валидацию входа/выхода, сохранение состояний знания | Исследовать после сравнения обычных функций и factories |
| `use process` | Ручное хранение стадий, ожиданий и восстановления | Durable history, корреляцию событий, версию, recovery semantics | Использовать существующий `use workflow`, отдельный синоним пока не нужен |
| `use action` | Повторяемую процедуру проверки/отправки/сверки внешней команды | Business operation identity, текущие полномочия, receipt и reconciliation | Сначала typed adapter поверх `use step`; имя без реализации не даёт гарантии |
| `use source` | Подключение источников и freshness metadata | Scope, источник, schema, effective/read time и понятную свежесть | Обычный read adapter; новая execution-директива пока избыточна |
| `use obligation` / `use contract` | Фиксацию принятых условий | Явное принятие, стабильную версию, amendments и authority | Предметная schema/factory; durable хранение отдельно |
| `use projection` / `use view` | Формирование отчёта, UI или документа | Выходную схему, разрешённые поля и consumer | Существующий `artifact` + renderer |
| `use policy`, `use invariant`, `use objective` | Назначение вычислений | Различимость ограничения, цели и гипотезы | Metadata/результат режима решения; не три новых runtimes |
| `use compensation` | Обработку неуспеха процесса | Самостоятельный согласованный обратный/исправляющий процесс | Тип операции/процесса; физический мир не откатывается автоматически |
| `use schedule` | Календарный запуск | Правила времени, окна, повторный запуск, пропущенные периоды | Trigger процесса |

Не следует смешивать публичный wire `DnaContract` нынешнего DNA с юридическим или исполняемым договором. Текущий экспорт описывает экспериментальный протокол. Он не хранит согласие сторон и не является authority для обязательств.

## 4. Математическая сторона предназначения функции

Обычная сигнатура `A → B` скрывает различие между расчётом, чтением сети, ожиданием и переводом денег. Полезнее рассматривать функцию как `A →[E] B`, где `E` описывает допустимые эффекты. Такое направление формализуют системы типов эффектов; в частности, Koka исследует effect types и их композицию. Это теоретическая опора для предлагаемого дизайна, а не утверждение, что DNA или TypeScript уже реализуют такую систему. [Leijen, Koka: Programming with Row Polymorphic Effect Types](https://arxiv.org/abs/1406.2061).

В нашей декомпозиции:

```text
Decision : Snapshot × ModelVersion → Knowledge<Result>
Process  : BusinessIdentity × EventHistory → NextIntentOrWait
Commit   : Intent × CurrentAuthorityState × Credentials → Outcome
```

Это спецификационные схемы, не точные типы API. Внешний commit также изменяет состояние authority; outcome может быть не установлен вызывающей стороной. Данные разных источников не образуют атомарный snapshot только потому, что собраны в один объект.

Для проверяемого поднабора можно потребовать `effects(function) ⊆ allowedEffects(mode)`. Например, decision разрешает чистое вычисление по переданным данным, process — вызов durable steps и ожиданий, action — конкретные capabilities. Произвольный импорт, closure, `fetch` или метод неизвестной библиотеки нельзя объявить безопасным одной строкой. TypeScript сам по себе не запрещает скрытые эффекты; нужны runtime isolation либо semantic checker с ограниченным профилем.

Из одного описания операции потенциально получаются различные исполнители: синтетический simulator, live authority adapter, recorder и fault injector. Общий интерфейс помогает сопоставлять их, но simulator не доказывает соответствие реального исполнителя. Для него нужны отдельные conformance tests.

Safety-свойство примера: если authority совершила активацию, в commit-контексте должны быть допустимые принятые условия и требуемая приёмка. Liveness-свойство: после получения всех оснований процесс когда-нибудь завершится либо выдаст явную нерешённую проблему. Второе зависит от доступности систем, доставки событий и правил повторов; durability сама по себе его не доказывает.

## 5. Почему direct-style может сократить нагрузку — и где цена

В текущем DNA автор явно указывает dependencies, затем использует соответствующие параметры callback, регистрирует узлы и заполняет assertions. Это сохраняет прозрачность, но добавляет технические решения вокруг короткого бизнес-правила.

Потенциальное упрощение: функция выглядит как обычное решение по типизированным входам, а связь с моделью и explanation metadata задаётся один раз в descriptor. Обычные условные операторы сохраняются; вложенный fluent builder для бизнес-control-flow не нужен.

Автоматически убрать и descriptor, и явные зависимости можно только ценой другого механизма. Статический compiler должен понимать обращения к фактам, helpers, closures, ветвления и библиотеки. Динамическая запись чтений видит только выполненную ветку и не заменяет консервативный граф всех потенциальных зависимостей. Эти два вида графа нельзя подменять друг другом.

Особенно опасна конструкция `if (!paid)`: отсутствующее значение не должно стать отказом в оплате через `undefined`. Сегодня DNA блокирует callback при неизвестной объявленной зависимости. Если новый профиль разрешит вычислить достаточный отказ по части входов, это **изменение семантики**, которому нужны собственные counterexamples и явное решение. Синтаксическое сокращение не должно внедрять его незаметно.

Не стоит скрывать за default текущую дату, выбор действующего договора, приоритет конфликтующих источников, широту полномочий и единицы денег. Именно эти различия определяют корректность бизнеса. Хорошая абстракция снимает механический учёт, сохраняя видимые основания решения.

## 6. Один durable бизнес-контракт

Под durable контрактом здесь понимается сохраняемая связь принятых условий, событий исполнения, ещё действующих обязательств и receipts. Это не обещание юридической исполнимости и не синоним блокчейна.

```mermaid
flowchart LR
  T[Принятые условия и версии] --> D[DNA: решение по snapshot]
  S[Сведения внешних систем] --> D
  D --> P[Durable процесс: ожидания и шаги]
  P --> A[Authority: актуальная проверка и commit]
  A --> R[Receipt либо исход не установлен]
  R --> S
  D --> V[Объяснение и бизнес-представления]
  P --> V
  R --> V
```

Для «Контур Site-1»: принятый заказ → подтверждённый аванс → резерв комплекта и исполнителя → монтаж → приёмка соответствующего scope → активация периода ПО. Гарантия и security support могут продолжаться после завершения workflow внедрения. Поэтому один бесконечный run на всю компанию или весь срок устройства не обязателен: связанные процессы могут иметь разные периоды и версии.

Минимальный payload между слоями должен явно нести:

- `agreementId`, `scopeRevision`, период и идентичность бизнес-операции;
- `modelVersion`, `snapshotId`, явное время оценки и ссылки на источники;
- decision outcome и причины, отдельно от текущего permission;
- command content, expected authority version и правило срока действия;
- receipt/rejection либо unresolved outcome с ключом для сверки.

Business operation key должен переживать retry и replacement run, но отличать новый реально разрешённый цикл операции. Например, повторная активация следующего SaaS-периода отличается period ID, а новая попытка активации того же периода сохраняет ключ. Authority проверяет совпадение содержимого при повторном ключе. Хеш payload фиксирует содержание, но не удостоверяет отправителя.

После долгого ожидания нужно новое получение актуальных данных и новая evaluation. Replay старого decision step воспроизводит прошлое решение и не обновляет его свежесть. Даже свежая оценка не устраняет гонку до commit: атомарная проверка принадлежит resource authority.

Версии принятых условий, модели DNA, workflow code и входных схем независимы. В опубликованной документации WDK описана привязка run к deployment и явные границы обновления; поведение `latest` зависит от backend. Исправление кода не должно менять цену старого договора или дублировать уже выполненную операцию при replacement run. [Workflow Versioning](https://workflow-sdk.dev/docs/foundations/versioning).

## 7. Обязательные контрпримеры интеграции

| Сбой | Ожидаемый результат |
|---|---|
| Резерв выполнен, ответ потерян | Тот же operation key; сверка с authority, исход до сверки не подменяется отказом |
| Два процесса видят последний комплект | Только одна подтверждённая бронь у inventory authority |
| Повторный start после завершения старого run | Повтор не создаёт вторую активацию того же периода |
| Доступ на площадку отозван во время ожидания | Старый verdict не разрешает новый выезд |
| Timeout, но первый worker продолжает работу | Fencing/expected version/deduplication у authority согласно её протоколу |
| Отмена пришла одновременно с отгрузкой | Сначала установить фактический исход; отменённый run не означает возвращённый товар |
| После отгрузки сорвался монтаж | Отдельный процесс исправления с расходами и подтверждениями; никакого фиктивного `undoShip` |
| Webhook приёмки пришёл рано, повторно или от другого scope | Доставка/дедупликация, scope и полномочия проверяются отдельно |
| Новая версия каталога опубликована во время ожидания | Принятые условия сохранены |
| Старый договор продолжен на новом workflow code | Явная migration boundary, сохранённые receipts и стабильные business keys |
| Unknown/conflict во входах decision | Ни false по умолчанию, ни разрешающий intent без достаточного основания |
| SaaS завершён, но поддержка устройства обещана дольше | Обязательство поддержки остаётся видимым |

Эти требования сформулированы по модели и независимому критическому разбору агента. Они ещё не проверены на Workflow SDK или live backend.

## 8. Какие библиотеки и продукты могут появиться

| Потребитель | Что получает из общей модели | Его отдельная ответственность |
|---|---|---|
| Визуализатор зависимостей | Факты, решения, версии, причины блокировки | Отличать потенциальное влияние от фактического изменения |
| Карта процесса / process monitoring | Переходы, ожидания, event history, сроки | Не выдавать dependency DAG за полный process graph |
| Портал договоров | Принятые условия, milestones, ещё действующие обязательства | Доступ пользователя и корректный scope |
| Симулятор бизнеса | Те же решения с синтетическими источниками и сценариями | Явные assumptions; отсутствие внешних эффектов |
| Проверка коммерческих обещаний | Связь публичного текста с offer, claims и evidence | Редакционное решение и публикация отдельно |
| Агент исполнения | Причины блокировки, разрешённые предложения следующих шагов | Сбор недостающих оснований; authority не передаётся модели языка |
| Библиотека операций склада/биллинга | Typed intents, keys, versions и receipts | Реальные гарантии конкретной системы |
| Smart-contract adapter | Узкие условия settlement и подтверждения | On-chain semantics, oracle, disputes, полномочия и отдельная верификация |

Блокчейн не наблюдает монтаж самостоятельно. Для офлайн-фактов нужны внешние источники/oracles; корректная запись чужого утверждения не доказывает физическую истину. Поэтому первый on-chain эксперимент, если появится потребность, лучше ограничить расчётом по явно подтверждённой вехе, с отдельной процедурой спора. [Ethereum: Oracles](https://ethereum.org/developers/docs/oracles/).

Из нынешнего DNA IR нельзя автоматически получить эквивалентный смарт-контракт: IR содержит схемы, IDs и зависимости, но не исполняемые callbacks. Понадобятся отдельный ограниченный профиль вычислений, правила чисел/округления и проверка эквивалентности. Даже одинаковые математические формулы могут расходиться из-за разной арифметики target runtimes.

## 9. Проверить уменьшение нагрузки, прежде чем расширять язык

Первое сравнение — один принятый заказ и решения о закупке/активации в трёх вариантах: обычные TypeScript-функции; текущий DNA; DNA с небольшими предметными factories и descriptors. Входы, outputs и отрицательные сценарии одинаковы. Если третий вариант лишь добавляет второй словарь поверх `fact/derive/rule/artifact`, отказаться от него.

Задачи читателя: найти принятую цену; изменить catalog без изменения старого договора; объяснить отрицательный cash при положительном результате; убрать приёмку; добавить конфликт источников; изменить часы монтажа; найти границу реального исполнения. Измерять правильность ответа, пропущенные и лишние изменения, обращения к документации и время. Строки кода — вспомогательный показатель. Агентные прогоны дают синтетическую проверку authoring, не эмпирическое исследование человеческой когнитивной нагрузки.

Второе сравнение — тот же process contract и fake authorities на простой сохраняемой state machine и выбранном WDK backend. Проверять падения до/после внешнего commit, повторный start, stale decision, раннее событие, отмену и смену версии. Отдельно измерять операционную сложность, трассировку и объём кода восстановления.

Только при устойчивой пользе direct-style authoring исследовать `use decision` на узком TypeScript-профиле. Критерии допуска: понятная семантика unknown/conflict, контролируемые effects, диагностируемые неподдержанные конструкции, stable identities, согласованные static graph и runtime trace, negative type/runtime contracts. Compiler размещать отдельным инструментом; ядро и обычные фабрики сохраняют независимость.

Бизнес-модель и проверенные расчёты находятся в [README.md](README.md), [economics.md](economics.md), [operations.md](operations.md), [validation.md](validation.md). Существующий `bun run verify` не подтверждает предлагаемые здесь новые runtime-возможности.

## 10. Общий принцип `.well-known`

В локальном Workflow проверены `packages/next/src/builder.ts`, `builder-eager.ts` и `packages/builders/src/base-builder.ts`. Next integration создаёт маршруты `/.well-known/workflow/v1/flow`, `/step`, `/webhook/[token]`. Кроме execution handlers, существует manifest; публикация его как статического `/.well-known/workflow/v1/manifest.json` включается через `WORKFLOW_PUBLIC_MANIFEST=1`. Это отдельный выбор, не обязательное публичное раскрытие всех внутренних функций.

В DNA сейчас `discovery()` проверяет документ с `dna`, `publisher`, `contracts`. Предложенный `/.well-known/dna` — экспериментальная discovery-точка, а не реализованный сервер, зарегистрированный стандарт или интерфейс выполнения. Сходство подходов полезно: стабильная машинная точка входа освобождает клиентов от знания внутреннего устройства проекта. Семантика публикации и исполнения при этом должна оставаться раздельной.

Возможный путь интеграции:

```text
business source
  → checked definitions and selected public capabilities
  → discovery document with schema/version/links
  → authenticated business API
  → durable workflow adapter
  → authority receipts and permitted status views
```

Public discovery может описывать доступные классы операций, входные/выходные схемы и требования доступа. Чтение этого документа не выдаёт разрешения на действие. Конкретные договоры, закрытые evidence, секреты и resume tokens не должны попадать в общую публичную проекцию. Внутренний workflow handler также не обязан быть внешним бизнес-API: клиенту нужен стабильный контракт действия, который переживает рефакторинг функции и смену runtime.

Поля operation schemas, scopes и auth requirements ещё отсутствуют в текущем `DnaDiscovery`. Их возможное добавление требует реального потребителя и проверки, что product-specific семантика остаётся в доменном пакете. Один интерфейс можно описать сначала отдельным приложением к discovery; общий протокол не должен заранее вобрать все будущие бизнес-процессы.

## 11. Какие инварианты уже находятся в типах

**Часть инвариантов DNA проверяется компилятором TypeScript; бизнес-истинность конкретного сценария проверяется отдельно.** Негативные контракты `tests/types.ts` подтверждают, что нельзя подать строку в числовой fact, выйти за enum роли, перезаписать computed через scenario assertion, вернуть неправильный тип из derive, использовать неверный тип dependency или передать async callback в синхронное правило. `ValueResult<T>` требует сузить status до `known`, прежде чем читать value.

При этом `s.number({ min: 0, integer: true })` выводит TypeScript `number`, а не refinement «неотрицательное целое». `unit` в Metadata — строковое описание; тип не запрещает сложение EUR и часов. Для проверки границы создан отдельный синтетический probe в игнорируемом `reports/business-model/type-boundaries.ts`: он прошёл TypeScript 7.0.2 и Bun 1.4.2. Отрицательное значение скомпилировалось и было отклонено schema runtime; смешанные единицы скомпилировались и дали known 102 для 100 EUR + 2 h. Это контрпример полноте гарантий, не желаемая новая арифметика и не исправление ядра.

| Инвариант | Где проверяется сейчас / должен проверяться |
|---|---|
| Тип поля, enum, форма результата, доступ к known value | TypeScript + runtime schema для внешних данных |
| Числовой диапазон, safe integer, валидность даты | Runtime schema/вычисление; не произвольная арифметическая теорема TS |
| Единицы, валюта, назначение идентификатора | В текущем ядре недостаточно различены типами; кандидат для небольшого доменного пакета |
| Соответствие receipt нужному договору/периоду | Статический scope там, где известен; обязательная runtime-проверка для внешних динамических IDs |
| Прибыль, кассовый остаток, доступные часы | Decision по supplied snapshot и явно заданным формулам |
| Отсутствие сети/мутации в произвольном callback | Текущий тип функции этого не доказывает; нужен effect checker/изолированный профиль |
| Актуальные полномочия, последняя единица склада, отсутствие повторного commit | Authority runtime, concurrency protocol и receipts |
| Истинность evidence и причинность экономии | Отдельные методы проверки источника/измерений; типовая метка не доказательство |

В tsops изучены `packages/core/src/config/definer.ts` и `types.ts`: const generics сохраняют имена приложений и namespaces; допустимые ссылки выводятся через `keyof`, а типы secret/config-map references отличаются от обычной строки. Это полезный образец: **из одной декларации выводить допустимые связи и операции**, сокращая повторный ручной ввод. Наличие secret name/key в типе не доказывает наличие непустого значения в окружении, а типизированный manifest не доказывает успешный deploy.

Для бизнес-пакета наиболее полезны следующие ограниченные типовые различия:

1. `Money<Currency>` и размерности/роли количества — с валидирующими constructors и явными операциями конверсии. Один brand поверх number не запрещает оператор `+`, который снова даст обычный number; закрытие арифметики требует согласованного API или semantic checker.
2. `Offer` и `AcceptedTerms` — разные входы; invoice строится по принятой версии. Сам переход принятия требует реального основания и не выполняется type assertion.
3. `CommandIntent` и `CommitReceipt` — разные результаты; dispatch не принимает произвольный бизнес-отчёт за permission, а reconciliation не принимает intent за факт исполнения.
4. `CheckedDecision` с scope/model/snapshot и `AuthorityReceipt` с operation identity — перенос результата проверки между слоями с сохранением контекста. Статическая оболочка помогает корректному коду, но не заменяет проверку при JSON-десериализации и не является криптографической capability.

TypeScript не имеет встроенного механизма одноразового потребления permission: alias позволяет использовать значение повторно, а внешний ресурс может измениться после проверки. Поэтому typestate «проверен → разрешён → исполнен» полезен как протокол программирования, но конечная операция всё равно должна проверить актуальные условия и дедупликацию.

Общая конструкция для уменьшения нагрузки: **типовая форма запрещает перепутать роли; evaluator устанавливает вывод по snapshot; authority подтверждает актуальное изменение; durable runtime сохраняет продвижение между ними.** Добавление директивы оправдано, если она помогает enforce именно этот договор выполнения и даёт понятные diagnostics. Автоматическое усиление гарантии из имени `Checked`, `Paid`, `Authorized` или `Durable` недопустимо.
