# Операционная модель «Контур Мониторинг»

Статус: проект предметной модели, 2026-09-05. Компания, продукт «Контур Site-1», заказы, мощности и сценарии вымышлены. Документ определяет будущие правила и вопросы проверки; он не подтверждает существование продукта, характеристики оборудования, выполнение SLA или соблюдение законодательства. Пилотная рамка: B2B-производства в Нидерландах, один объект на первоначальный договор; расчёты в EUR. География требует отдельной проверки применимости правил до реальной продажи. Числа экономики принадлежат [economics.md](economics.md); операционные параметры ниже не переопределяют цены или объёмы продаж.

Основной результат бизнеса — работающий измерительный контур и доступ к интерпретируемой истории энергопотребления на согласованных точках. Приборы только наблюдают: нет управления станками, защитных отключений, обещаний предотвращения аварий, сертифицированного расчётного учёта или гарантированной экономии. Даже read-only интеграция может влиять на сеть и оборудование нагрузкой опроса; отсутствие команд управления само по себе не доказывает безопасность подключения.

## 1. Что именно продаётся и обслуживается

В первоначальном пакете один gateway, один утверждённый трёхфазный измеритель энергии и совместимый набор трансформаторов тока для **одной точки измерения**, плюс питание/корпус/соединительные принадлежности согласно версии BOM. Это граница предполагаемого пакета, а не готовый электрический проект: точные модели, количества и номиналы ещё должны быть выбраны и проверены. Заказчик предоставляет согласованные питание и сеть; пригодность существующей установки должна быть отдельно подтверждена. Одна точка не означает наблюдение каждого станка цеха. Список типов датчиков, количеств, питания, соединений и допустимых вариантов монтажа нельзя заменять словами «датчики в комплекте». Для каждой площадки нужна совместимость конкретной конфигурации. Дополнительные линии, новые протоколы, нестандартные шкафы, новые места установки и доработка интеграции — изменение объёма работ.

Предпочтительная первоначальная производственная модель — закупка готовых компонентов, комплектация, настройка и проверка комплекта. Собственное изготовление электроники не предполагается. Если поставщик выпускает компоненты под собственной маркой, отдельная проверка должна установить возникающие роли и обязанности; слово «интегратор» не решает этот вопрос.

| Объект обязательства | Измеримый результат | Что не следует из результата |
|---|---|---|
| Поставка | Согласованные позиции и количества переданы по договорному событию | Монтаж выполнен; подписка началась; экономия достигнута |
| Монтаж | Комплект установлен по согласованному проекту; монтажный протокол | Все данные правильны; заказчик принял услугу |
| Наладка | Точки, масштабы, часы, связь и тестовые данные проверены по версии процедуры | Приёмка автоматически подписана; сеть будет всегда доступна |
| Приёмка | Уполномоченная сторона приняла конкретный объём/этап | Весь будущий сервис бездефектен; оплата поступила |
| SaaS | Доступны определённые функции, хранение и сервисные показатели | Местная сеть, питание и измерители исправны |
| Поддержка | Реакция и работа в согласованных часах и каналах | Устранение любой проблемы к моменту первой реакции |
| Гарантия | Применимые действия по подтверждённому дефекту и условиям конкретной поставки | Неограниченный бесплатный выезд или новая гарантия на весь объект |
| Security support | Обработка уязвимостей и обновления в обещанный срок и объёме | Новые функции и бессрочная совместимость |

## 2. Идентичности: не объединять разные жизненные циклы

Ниже обычные предметные записи, а не предложение универсальной онтологии. `id` — стабильная идентичность; `revision` — изменяемая спецификация или версия записи; `effectiveFrom/effectiveTo` задают период применимости. Для всех записей с внешним владельцем нужны `sourceSystem`, `sourceRecordId`, `sourceVersion`, `observedAt` и область применимости. Эти ссылки ещё не аутентифицируют источник.

| Запись / ключ | Минимальные поля | Владелец и принцип изменения |
|---|---|---|
| Customer / customerId | договорная сторона, billingAccountId, статус отношений | CRM/договорной реестр; не равен SaaS tenant |
| Site / siteId | customerId, timezone, доступные окна, ответственные роли, сеть, среда | Реестр площадок + подтверждение заказчика; перемещение оборудования не переписывает старую площадку |
| Monitored asset / assetId | siteId, обозначение линии, тип, точки измерения, сроки действия привязки | Заказчик подтверждает соответствие реальному объекту; станок и датчик — разные объекты |
| Hardware model / modelId + hardwareRevision | производитель, модель, интерфейсы, диапазоны, условия среды, документы | Инженерный каталог; изменение новой ревизии не меняет установленные экземпляры |
| BOM / bomId + revision | позиции, количества, допустимые замены, совместимые firmware и процедуры | Инженерный выпуск; «аналог» требует явного одобрения конфигурации |
| Physical unit / unitId | serial, model/revision, lot, custody, location, condition, firmware, warrantyReference | Серийный реестр + склад; MAC/IP/сертификат не заменяет serial |
| Logical identity / deviceIdentityId | unitId, credential references, tenant/site binding, validity, revocation | Текущая система управления доступом; секреты в DNA не импортируются |
| Firmware / releaseId | совместимые ревизии, digest, release status, support end, migration path | Release authority; desired version и реально подтверждённая версия отдельно |
| Offer / offerId + revision | BOM scope, функции, объём внедрения, сроки действия, условия | Каталог; используется для нового предложения |
| Accepted order / orderId + amendment | accepted offer snapshot, site, quantities, milestones, agreed terms | Договорной реестр; изменения только согласованным дополнением |
| Deployment / deploymentId + configurationRevision | order scope, site, mapped units/points, procedure, milestones | Delivery owner; один заказ может вводиться этапами |
| Work package / workId | требуемые роли/часы, предшественники, окно, acceptance evidence | План работ; факт часов отдельно от оценки |
| Resource commitment / reservationId | resourceId, role, window, quantity, expiry, operation receipt | Авторитетный календарь/склад, а не расчёт DNA |
| Subscription / subscriptionId + termId | tenant, contracted units/site scope, activation event, term, renewal terms | Реестр согласованных подписок; текущий тариф не меняет старый term |
| Telemetry point / pointId + mappingRevision | physical quantity/unit, sensor/channel, scale, asset binding, sampling policy | Конфигурация измерения; привязка действует в конкретном периоде |
| Acceptance / acceptanceId | scope revision, accepted/rejected items, conditions, actor authority, time | Подтверждение заказчика и проверенный процесс приёмки |
| Incident / incidentId | affected scope, times, severity reason, attribution evidence, work log | Support/incident authority; закрытие тикета не доказывает устранение |
| RMA / rmaId | failed unit, diagnosis, disposition, replacement unit, cost responsibility | Гарантийный реестр; новый serial связан с прежним, не заменяет историю |
| Operation / operationId | intent digest, idempotency key, expected version, receipt, outcome | Выполняющая система; `outcome=unknown` сохраняется после неоднозначного timeout |

Серийный номер физического прибора и логический идентификатор могут отличаться. Это предметное разделение согласуется с NISTIR 8259A, §2, Table 1, Device Identification; источник не подтверждает реализацию такой возможности в вымышленном комплекте. [NISTIR 8259A, май 2020](https://nvlpubs.nist.gov/nistpubs/ir/2020/NIST.IR.8259A.pdf).

## 3. Независимые автоматы состояний

Один `customer.status=active` не подходит. Физический прибор может быть исправен, подписка приостановлена, гарантия действительна, право на security updates сохранено. По каждому переходу фиксируются прежняя версия, событие, автор, время действия и квитанция. `unknown` и `conflict` — состояние знания о факте, а не придуманные коммерческие состояния клиента.

Общее правило: неизвестный обязательный guard означает «не установлено, запросить факт», конфликт — «разрешить расхождение явным процессом». Они не означают «клиент отклонён». Подтверждённый отрицательный guard даёт отказ с конкретной причиной. Любое реальное действие повторно проверяется своей authority в момент выполнения.

### 3.1 Поставка и физическая единица

| Переход | Guard / обязательные основания | Effect / подтверждение | Authority и время |
|---|---|---|---|
| BOM draft → released | совместимость, комплектность, инструкции, утверждённая проверка | неизменяемая release revision | Engineering; действует с даты выпуска |
| Demand → purchase approved | допустимый поставщик/позиция, согласованный бюджет и потребность | заявка на закупку; ещё нет доступного остатка | Procurement/finance |
| Purchase approved → ordered | внешнее размещение и подтверждение заказа поставщиком | supplier orderId, обещанное окно доставки | Procurement; обещанный срок не факт прибытия |
| Supplier order → assembled/tested у поставщика | документы конкретной партии и спецификации, если доступны | производственная запись поставщика | Supplier; отсутствие данных не «test passed» |
| Ordered → received/quarantine | полученные units/количества, custody evidence | физическое наличие в карантине, разницы с заказом | Warehouse; arrivalAt |
| Quarantine → available | входная проверка, revision match, serial uniqueness, годность | пригодные units доступны к резерву | QA/warehouse; releasedAt |
| Available → reserved | текущее наличие, нет другого действующего резерва | атомарный резерв на order/window с expiry | Inventory authority; committedAt |
| Reserved → configured/tested | совместимый firmware, комплектность, стендовая процедура | конфигурация + тестовый протокол конкретных units | Workshop; testAt |
| Tested → shipped | разрешённая отгрузка, действующий резерв, shipping manifest | units выбыли со склада, carrier receipt | Warehouse/carrier; shippedAt |
| Shipped → delivered | подтверждение доставки и полученных позиций | custody changed; delivery exceptions отдельно | Carrier/customer; deliveredAt |
| Delivered → installed | site readiness, допуск, проект, квалифицированный исполнитель | installation record; actual mapping | Delivery/site authority; installedAt |
| Installed → operating | подтверждена наладка и допустимость подключения | operational baseline, health measurement | Engineering; commissioning completion |
| Operating → quarantined/removed | дефект/инцидент/решение об отключении именно измерительного комплекта | прекращение использования, сохранение следов | Incident owner/site; affected interval |
| Removed → returned | RMA, согласованная упаковка/обращение с данными, transport | return custody record | Service/logistics |
| Returned → repair / refurbish / scrap | диагноз, допустимость ремонта, data disposition, стоимость | disposition record, новая проверка перед складом | QA/service; нельзя сразу в available |
| Reserved → released | cancellation/expiry подтверждены, нет начатого необратимого действия | резерв снят; расходы отмены отдельно | Inventory authority |

Производственные данные изготовителя — вход для прослеживаемости, но не основание объявлять весь смонтированный контур проверенным. Неисправные и возвращённые изделия не смешиваются с доступным складом.

### 3.2 Внедрение, договор и подписка

| Переход | Guard | Effect / что остаётся отдельным | Authority / время |
|---|---|---|---|
| Opportunity → qualified | согласованная проблема, подходящая площадка, ответственные роли | допустимость дальнейшего обследования; не выигранная сделка | Sales + engineering |
| Qualified → surveyed | достаточные сведения о точках, сети, среде, доступе | версия site survey и список неизвестного | Site + delivery |
| Surveyed → proposed | версия BOM и scope, оценка effort, условия поставки | новое коммерческое предложение с validity | Sales; capacity только оценена |
| Proposed → accepted | подтверждённое принятие конкретной версии уполномоченной стороной | accepted terms + условные обязательства | Contract authority; acceptedAt |
| Accepted → scheduled | обязательные согласования, текущие резервы материалов/людей/окон | подтверждённое окно работ | Delivery + booking authorities |
| Scheduled → started | доступ сохраняется; допуск и readiness актуальны на день выезда | фактический старт и потребление ресурсов | Site/delivery; actualStart |
| Started → commissioning | монтаж зафиксирован; конфигурация и данные достаточны | запуск процедуры приёмочных измерений | Engineering |
| Commissioning → technically ready | критерии ниже выполнены для конкретного scope | технический протокол; billable ещё определяется договором | Engineering; готовность имеет срок/контекст |
| Technically ready → accepted / partially accepted / rejected | ответ по пунктам и полномочия принимающего | принятый объём, defects, remedial due dates | Customer acceptance process |
| Accepted scope → activation requested | договорный trigger наступил, scope однозначен | intent активации; ещё не действующий entitlement | Contract/billing boundary |
| Activation requested → active | текущая authority атомарно создала term/entitlement, вернула receipt | actualActivatedAt, срок, функции | Subscription authority |
| Active → renewal offered | approaching term end, support horizon, актуальный каталог | предложение следующего term; старый неизменен | Sales/contract |
| Renewal offered → renewed | принято новое условие до/после окончания по политике | новый term, effective date; нет заднего переписывания | Contract/subscription |
| Active → grace / suspended | договорный trigger, проверенное событие, разрешённое уведомление/период | ограничения SaaS согласно согласованным terms | Billing/entitlement authority |
| Suspended → active | устранены основания, восстановление подтверждено | новые операции доступа разрешены; данные восстановлены только если сохранены | Subscription authority |
| Active/suspended → terminated | действительная процедура завершения/дата | остановка нового сервиса, export/deletion workflow | Contract + data authority |
| Terminated → decommissioned | снятие привязки, отзыв credentials, предусмотренное обращение с данными/железом | подтверждения по каждому действию | Site + identity + data authorities |

Приёмка по умолчанию явная, по пунктам. Молчание не равно приёмке. Если будущий договор предусматривает иной процесс, это отдельная проверяемая политика с нужными событиями и юридической проверкой. Начало SaaS определяется согласованным activation trigger; доставка, техническая готовность, приёмка и оплата не взаимозаменяемы. Частичная приёмка создаёт billable scope только если договор допускает такое разбиение.

### 3.3 Инцидент и замена

Incident: `reported → triaged → investigating → workaround/restored → monitored → resolved → closed`. Обходное решение не обязано устранять первопричину. `restoredAt` требует измерения восстановления сервиса; `closedAt` — завершение процесса. Повторная деградация связывается с прежним incident, но не стирает промежуток восстановления.

RMA: `requested → diagnosis pending → eligible/ineligible/disputed → authorized → replacement reserved → dispatched → received/installed → validated → failed unit returned → settled`. Возврат старого прибора и установка нового могут идти параллельно по согласованной политике advance replacement. Даты и ответственность за невозврат отдельны. Замена не удваивает платные точки; cutover задаёт периоды привязки старого/нового serial к одному pointId. Новая гарантийная дата только по явно применимым условиям, не автоматически.

## 4. Исполнимость плана и фактически занятые ресурсы

Для каждого work package задать role, skills evidence, effort estimate/range, travel, location, dependencies, earliestStart, deadline и календарь. Квалификация, доступность и текущее разрешение входа — разные факты. Требование производителя работать с квалифицированным персоналом показано, например, в PowerTag Design and Commissioning Guide, разделе Important Information. Это основание включить проверку квалификации, а не инструкция по электрическому монтажу или подтверждение допуска для Нидерландов. [Schneider Electric, Important Information](https://productinfo.se.com/powertagdesigncommguide/powertag-design-comm-guide/EN/BM_PowerTag%20Design%20and%20Comm%20Guide_0000468594.xml/%24/Definition_Important_Information_0000417345).

| Роль | Ограничивающая работа | Нельзя считать взаимозаменяемой с |
|---|---|---|
| Solution engineer | обследование, совместимость, scope | продавцом, который подтвердил интерес |
| Закупщик / склад / QA | заказ, приёмка, выпуск, комплектование | поставщиком, сообщившим дату |
| Квалифицированный монтажник | площадочный монтаж по применимым правилам | удалённым инженером поддержки |
| Commissioning engineer | mapping, масштабы, connectivity, испытания | комплектовщиком со стендовым тестом |
| Site authorized contact | доступ, остановочные окна, подтверждение объекта | любым пользователем SaaS |
| Customer IT | сеть, допустимые интерфейсы, credentials/process | начальником цеха без IT-полномочий |
| Support / incident owner | очередь и согласованный канал реакции | всей численностью компании |
| Firmware/security owner | поддерживаемые версии, vulnerability response | billing, который остановил SaaS |

Плановая свободная мощность роли r за окно w:

`freeHours(r,w) = workingHours − leave − training − fixedOps − existingCommittedHours − explicitContingency`.

Нужны единицы «человеко-часы конкретной роли в окне», не просто «20 свободных часов». Capacity не может быть отрицательной без явного overcommitment. Общая сумма достаточна лишь как необходимое условие: один специалист не может одновременно присутствовать на двух площадках, а незаменимые роли и непрерывные окна проверяются отдельно. Резерв инцидентов не складывается с остатком capacity второй раз. Effort actual используется для оценки ошибки планирования, не для заднего изменения заказа.

Для ориентировочного critical path:

`earliestStart(work) = max(finish(predecessors), materialReadyAt, siteWindowStart, staffReadyAt)`;

`earliestFinish = calendarAdd(earliestStart, duration)`.

Неизвестное materialReadyAt не превращается в сегодня. Диапазоны lead time дают диапазон даты, не автоматически вероятностный p90. Подтверждение обещанного срока требует одновременно выполнимого расписания, достаточных резервов, актуальной готовности площадки и принятого обязательства. DNA может выдать candidate plan, а запись обязательства должна иметь квитанцию системы бронирования.

В первой реализации обойтись маленьким конечным календарём и явными задачами. Если подбор расписания становится самостоятельной потребностью, сравнить ручную эвристику с решателем ограничений; не прятать оптимизатор в универсальный граф DNA.

### Проверка операционной предпосылки финансовых сценариев

В [economics-check.py](economics-check.py) считаются 4 и 24 площадки с январской поставкой/внедрением и активацией с 1 февраля. Чтобы этот cash schedule стал исполнимым планом, до принятой даты должны быть обеспечены все комплекты, монтаж, наладка, окна заказчиков и применимые приёмки. Доход, начинающийся 1 февраля в расчёте, не доказывает возможность физически подготовить 24 объекта в январе.

Для проверки масштаба предлагаем **синтетический planning probe**, не норму трудозатрат: на одну площадку 6 часов квалифицированного монтажа/проверки, 2 часа интеграции/наладки, 1 час координации и 1 час обучения. В маленьком календарном контрпримере последние три задачи выполняет один deployment engineer. Всего 10 прямых часов согласованы с экономической предпосылкой `10 ч × €50 + €100 travel allowance = €600/site`; стоимость и роль не подтверждены котировками. Travel time, складской QA, переделки, ожидание доступа и текущая поддержка добавляются к workload отдельно; €100 уже включены в direct cash cost, но сами по себе не задают время поездки. Отдельное предпродажное обследование не считается бесплатно включённым в час координации: его стоимость/часы должны учитываться по принятой политике acquisition/pre-sales.

| Только эти три работы | 4 площадки | 24 площадки |
|---|---:|---:|
| Монтаж подрядчиком | 24 ч | 144 ч |
| Наладка | 8 ч | 48 ч |
| Координация | 4 ч | 24 ч |
| Обучение | 4 ч | 24 ч |
| Всего без поездок, ожиданий, QA и переделок | 40 ч | 240 ч |

Если один и тот же deployment engineer выполняет координацию, наладку и обучение 24 объектов, ему нужны минимум 96 часов до учёта поездок и операционной нагрузки. Достаточность такого месяца неизвестна без календаря и броней; чистое сложение часов не доказывает совпадение допустимых окон. Монтажные 144 часа также требуют конкретных ресурсов/дат и квалификации. €600 direct deployment allowance на площадку в финансовом сценарии — стоимость-предположение, а не подтверждённая котировка или право на эти часы. Все 10 часов здесь относятся к прямым оплачиваемым подрядным затратам проекта и исключены из fixed €2400/month. Если позже их выполняет штат, уже полностью оплаченный в fixed costs, экономику нужно согласованно переразнести: не вычитать одну зарплату одновременно в direct и fixed costs.

24-площадочный сценарий получает операционный статус `conditional/unproven` до выполнения этих условий. Если не хватает ресурсов, переносится фактическая приёмка/активация и связанный cash schedule; согласованный deadline сохраняется как обязательство с риском нарушения. Разработка продукта, его инженерная проверка, создание cloud service и procurement readiness предполагаются выполненными до такого delivery cohort; соответствующие startup costs и elapsed time исключены из этого probe, а не равны нулю.

Для конкретного отрицательного теста зададим ещё один полностью вымышленный календарь: комплекты выпущены входным QA 15 января 2027; один deployment engineer и один field installer доступны только 18–29 января, каждый по 10 рабочим дням × 8 ч = 80 ч. Координацию в этом ограниченном тесте тоже разрешаем лишь в данном окне; обучение должно следовать за нужными ему наладкой/приёмкой по процедуре. Другой персонал, overtime и выходные не предполагаются. Это тестовый календарь, не утверждение о реальной команде или национальном календаре праздников.

| Cohort | Deployment engineer: need / available | Field installer: need / available | Вывод |
|---|---:|---:|---|
| 4 площадки | 16 / 80 ч | 24 / 80 ч | Необходимое условие по сумме часов пройдено; нужен план зависимостей/окон |
| 24 площадки | 96 / 80 ч | 144 / 80 ч | Условие нарушено: дефицит 16 и 64 ч; 1 февраля с этими ресурсами неисполняемо |

Дефицит возникает ещё до travel, QA и переделок. Такой сценарий должен дать известный отрицательный capacity result, а не `unknown`: входы в пределах теста заданы, противоречие арифметическое. Оно не доказывает невозможность роста при иной команде; альтернативный сценарий может добавить подтверждённые ресурсы, расширить окно или разбить ввод на партии и пересчитать денежные события.

## 5. Материалы, запас и обратная логистика

Запас ведётся по пригодной конфигурации, месту и моменту, а не одной цифрой «devices». Для серийных единиц множество available не пересекается с reserved, quarantine, shipped и installed. `onHand` включает физически лежащий карантин, поэтому не равно available-to-promise.

`ATP(t | snapshotAt,sku,revision,location) = eligibleGrossOnHand(snapshotAt) + futureConfirmedEligibleReceipts(snapshotAt,t) − unfulfilledCommittedDemandDueBy(t) − unallocatedServiceReserve`.

Здесь gross — все физически находящиеся на складе пригодные единицы **включая уже зарезервированные**, исключая карантин, отгруженное и установленное. Поэтому действующие неисполненные резервы вычитаются в committed demand ровно один раз. Future receipts содержат только ещё не полученные поступления после snapshotAt и не позднее t; поступивший товар переносится в onHand и удаляется из incoming. Service reserve содержит только дополнительно выделенную квоту, ещё не включённую в committed demand; один резерв нельзя вычесть дважды. Если upstream отдаёт уже unreserved available, адаптер использует другую явно определённую формулу без повторного вычитания этих резервов. Отрицательный прогноз — дефицит, не округлённый ноль.

Это прогноз; приход с неопределённой датой показывает альтернативный сценарий. Прогноз не создаёт reservation. Входящие количества нельзя считать и готовым комплектом, и компонентами этого же комплекта одновременно. Нужные кратности BOM: kitAvailable = минимум целых комплектов по всем обязательным позициям. Заменяемость хранить матрицей утверждённых комбинаций; похожий разъём не доказывает совместимость.

Lead time разделить на supplier queue, manufacture, transport, incoming QA, kit preparation, site access и commissioning. Замерять отдельно обещанный и фактический сроки, долю недопоставок и доработки после приёмки. MOQ, cancellation terms и cash prepayment передаются в экономику; ETA не означает право отменить обязательство бесплатно.

Service reserve для гарантий конкурирует с новой продажей. Политика приоритета должна быть явной: release запасной единицы в продажу требует новой оценки ремонтопригодности активного парка и обещаний замены. Для первого пилота допускается вручную выбранный резерв; статистическая оптимизация требует наблюдений о парке, возрасте и отказах. Формула средний спрос × средний lead time не задаёт гарантию отсутствия дефицита.

Обратная логистика включает return authorization, shipping/custody, проверку serial, диагностическое время, доступ к журналам с разрешением, удаление/сохранение данных по применимой политике, supplier credit, repair/refurbishment costs, повторный QA и disposal. «Гарантия производителя» не означает, что локальный выезд и подменное оборудование бесплатны поставщику сервиса.

## 6. Что доказывает техническая готовность

Приёмочная процедура привязана к deployment scope revision, BOM, firmware, point mapping и timestamp. Минимально проверяет:

1. Фактически установленные units и точки совпадают с согласованным scope либо есть одобренное отклонение.
2. Зафиксированы нужные инженерные условия и документы квалифицированного монтажа; без конкретного изделия документ не задаёт электрические инструкции.
3. Клиент подтвердил соответствие pointId реальному объекту; подпись датчика «Линия 1» не доказывает правильную привязку.
4. Физическая величина, единица, коэффициент, знак, диапазон и поведение счётчика описаны и проверены применимым способом. Поверка/калибровка/проверка plausibility не считаются синонимами.
5. Версия firmware совместима; реально применённая конфигурация подтверждена устройством и проверкой результата.
6. Tenant и site binding верны; проба из одного tenant не видна неуполномоченному другому tenant.
7. Event time, ingestion time и clock-quality зафиксированы; будущий timestamp не принимается за свежесть.
8. Проверены нормальная передача, разрыв связи, восстановление и ожидаемая политика буфера в согласованном тестовом сценарии.
9. Показатели completeness и latency определены для известной частоты и набора точек; ноль потребления отличим от отсутствия выборок.
10. Каналы технических уведомлений проверены контролируемым событием; доставка уведомления и действия человека отдельно.
11. Заказчик получил эксплуатационные границы, escalation path и описание прекращения сервиса.
12. Все существенные отклонения указаны явно; принятые исключения не меняют обещания остальным клиентам.

Конкретные tolerances, sample interval, test duration, сеть и модели приборов ещё должны быть утверждены как versioned acceptance policy. Пока они неизвестны, нельзя вывести `technicallyReady=true`. Полнота списка требований здесь не заменяет выполненные испытания.

## 7. Телеметрия, связность и границы сервиса

Для каждого значения хранить `pointId`, `mappingRevision`, `eventAt`, `receivedAt`, `sequence/batchId`, `value`, `unit`, `quality`, `clockQuality` и происхождение. Для агрегата — интервал `[from,to)`, ожидаемую область, число ожидаемых/полученных валидных уникальных выборок, late-arrival cutoff и calculation revision.

| Понятие | Проверяемое определение | Неправильный вывод |
|---|---|---|
| Device connected | подтверждение конкретной сессии связи и актуальность | датчики корректны и поступают данные |
| Heartbeat fresh | возраст последнего heartbeat в пределах политики | энергия известна за этот же период |
| Measurement fresh | доверенная шкала времени, возраст валидного измерения допустим | весь час заполнен без пропусков |
| Historical completeness | доля валидных уникальных наблюдений в ожидаемом наборе | эти наблюдения пришли вовремя |
| Cloud available | определённый endpoint успешно отвечает с заданным качеством | площадка имеет питание/интернет |
| Meter operational | применимые диагностические проверки пройдены | данные описывают нужный станок |
| Potential opportunity | заданное правило обнаружило паттерн в пригодных данных | установлена причина перерасхода/доказана экономия |

Нельзя применять «последнее полученное сообщение победило» к любому состоянию связи. AWS IoT Core прямо допускает дубликаты и изменение порядка lifecycle events; порядок нужно восстанавливать с учётом сессии/версии, а не только времени прихода. Это конкретный пример инфраструктурного поведения, не выбор AWS для продукта. [AWS IoT Core, Lifecycle events, разделы Connect/Disconnect events и Handling client disconnections](https://docs.aws.amazon.com/iot/latest/developerguide/life-cycle-events.html).

Edge buffering — отдельная заявленная возможность с параметрами local durable storage, usableBytes, recordBytes, sampleRate, expiry, overflow policy, export bandwidth, encryption и recovery after reboot. Приближённый горизонт `usableBytes / bytesPerSecond` допустим только при указанных предпосылках и запасе; реальная проверка должна учесть overhead, filesystem, частоту записей и питание. Доставка после восстановления не устраняет прошлое нарушение timely delivery. Повторы дедуплицируются; суммирование дублей не увеличивает потребление.

Persistent MQTT session не является архивом всей телеметрии устройства: хранение ограничивается семантикой сессии, QoS, лимитами и expiry. Буфер данных от датчика к облаку нужно проектировать отдельно. [AWS IoT Core, MQTT, Message traffic after reconnection to a persistent session](https://docs.aws.amazon.com/iot/latest/developerguide/mqtt.html).

Свойство «данные шифруются» также раскладывается по участкам. Например, документация Greengrass Stream Manager описывает политики локального хранения/экспорта и отдельно предупреждает об отсутствии собственного шифрования локального stream storage и передачи между local components. Поэтому будущий выбор edge stack требует проверять storage, local IPC и cloud transport отдельно; никакой AWS stack здесь ещё не выбран. [AWS IoT Greengrass, Manage data streams, Data security](https://docs.aws.amazon.com/greengrass/v2/developerguide/manage-data-streams.html).

Энергия и мощность не взаимозаменяемы. Для energy counter нужны reset/wrap semantics и проверка monotonicity; для интегрирования мощности — правило временных интервалов и пропусков. Неизвестные интервалы не заполняются нулём. Отрицательные значения не отбрасываются без понимания возможного направления потока. Точность физического контура включает выбранный прибор, датчик, монтаж, scaling и режим; спецификация одной компоненты не переносится автоматически на весь контур.

## 8. SLI, SLO и контрактный SLA

SLI — определённое измерение, SLO — выбранная цель, SLA — принятое договорное обязательство и remedy. Ни одна цифра SLO в расчётном сценарии не доказывает способность соблюдать SLA. До пилота численные пороги и сервисные часы находятся в реестре политик; обещание 24/7 не подразумевается.

| Показатель | Точная основа измерения | Нужные параметры и исключения |
|---|---|---|
| Cloud availability | доля успешных квалифицируемых probe/request intervals | endpoints, tenant scope, timeout, probe geography, interval, scheduled exclusions |
| Timely measurement coverage | valid unique expected samples received before deadline / all expected samples | expected point set version, cadence, allowed lateness, clock uncertainty |
| Historical completeness | valid unique received samples / expected samples к data cutoff | backfill, duplicate treatment, invalid payload reasons, denominator revision |
| Freshness | evaluationAt − latest eligible eventAt | maximum age, clock check; неизвестный clock → freshness unknown |
| Support first response | часы выбранного service calendar от valid ticket receipt до meaningful response | timezone, calendar, severity assignment, channel; автоответ не реакция |
| Restore time | serviceImpactStart → verifiedRestoreAt, с явно учтёнными pauses | начало обнаружено/оценено, evidence, customer-wait rules; resolution отдельно |
| Warranty dispatch | authorizedReplacementAt → carrierHandoverAt | рабочий календарь, agreed stock class; доставка/монтаж не dispatch |
| Data export completion | authorized export request → доступность проверенного файла | scope, format, срок доступа, authentication, size policy |
| Security support coverage | обещанные модели/версии/сроки имеют процедуру обработки и канал обновления | fixed support end, escalation, supplier dependency, update applicability |

Для availability `A = 1 − excluded-adjusted union(downtime intervals) / eligibleDuration`. Пересекающиеся outages считаются объединением интервалов, не суммой. Если eligibleDuration=0, показатель `not applicable`, не 100%. Пропущенные probe observations дают coverage/unknown, а не успех. Агрегация по fleet должна показывать распределение по площадкам: хороший общий средний показатель не скрывает один постоянно недоступный объект.

SLA exclusions — предлагаемые договорные категории: подтверждённое питание/локальная сеть заказчика вне согласованного service scope, согласованные окна обслуживания, неподдерживаемые несанкционированные изменения. Причина должна иметь доказательство и период, и исключения не могут вводиться после инцидента. Облако поставщика или его подрядчик не считаются исключением автоматически. Спор об attribution остаётся `disputed`; отдельно считать customer-experienced impact и contract-attributed impact.

Кредит за SLA вычисляется только по согласованной версии условий: eligible fee component, breach tier, cap, claim/automatic process и approvals. Он не уменьшает hardware invoice или отменяет договор без соответствующего основания. До выбранного договора это candidate remedy, не признанная обязанность.

## 9. Firmware, поддержка и завершение жизненного цикла

Матрица `hardwareRevision × firmwareRelease × protocol/configRevision × supportWindow` определяет разрешённые комбинации и путь миграции. Не весь старый firmware немедленно опасен, не вся новая версия подходит старому железу. Наличие release не означает, что конкретное устройство обновлено. Для OTA нужны current authorization, совместимость, подтверждение применения, recovery policy и разрешённое окно. Допустимое отклонение обновления заказчиком фиксируется вместе с последствием, не скрывается как «latest».

NISTIR 8259A, §2, Table 1 содержит отдельные категории configuration, data protection, interface access, software update и cybersecurity state awareness. Мы используем их как вопросы к проекту и входным данным; это не сертификация, не утверждение соответствия NIST и не исчерпывающий перечень правовых обязанностей. [NISTIR 8259A](https://nvlpubs.nist.gov/nistpubs/ir/2020/NIST.IR.8259A.pdf).

Установить разные даты и основания: end of new sales, last order, supplier component EOL, end of feature updates, end of security support, end of paid service, customer-specific contract end, warranty end, retention/deletion date. Прекращение SaaS по неоплате не отменяет ранее обещанный срок security support для проданной единицы. Смена supplier policy создаёт риск исполнения наших уже принятых обязательств, а не автоматически сокращает их.

При завершении проверить отдельно: экспорт в пределах полномочий, остановка новых данных по согласованной процедуре, отзыв logical identity, отвязка tenant/site, локальные сохранённые данные, данные облака/backup, сроки договорного/правового хранения, физическое снятие или продолжение владения заказчиком. Отзыв сертификата не удаляет локальный диск, удаление tenant не доказывает выполнение всей retention policy. Повторное использование unit допускается после контролируемого data disposition и новой provisioning identity.

## 10. Полномочия и атомарные операции

| Действие | DNA может вывести | Что должна обеспечить внешняя authority |
|---|---|---|
| Предложить срок внедрения | feasibility по snapshot и основания | актуальное резервирование людей, материалов и окна |
| Обещать комплект | candidate ATP и compatible BOM | атомарный inventory reserve, expiry и receipt |
| Выставить кандидат счёта | принятый milestone + agreed fee | создание единственного invoice, бухгалтерские/налоговые правила |
| Активировать SaaS | trigger выполнен по snapshot | current authorization, единственный term/entitlement, receipt |
| Обновить firmware | compatibility + proposed permission | authenticated current actor/device, version precondition, execution evidence |
| Приостановить сервис | кандидат основания и ожидаемый эффект | актуальное договорное основание и permitted process, current identity checks |
| Выдать RMA | policy eligibility или unresolved facts | актуальное одобрение и единственный reserve replacement |
| Экспортировать данные | permitted scope candidate | текущая проверка получателя/полномочий и защищённая выдача |

Каждый intent содержит scope, expected source versions, expiresAt и stable idempotency key. Timeout после записи даёт `unknown outcome`; сначала lookup receipt по ключу. Новый ключ может создать дубль. При изменённом intent прежний ключ нельзя использовать как доказательство принятия нового содержания. Snapshot approval не служит bearer token без внешне реализованного механизма.

Stock reserve + calendar reserve + subscription activation могут принадлежать разным системам. Общая успешная оценка не является общей транзакцией. В пилоте допустим координируемый вручную commitment checklist с квитанциями; при partial failure фиксировать уже сделанное, expiry, компенсацию и расходы, а не возвращать все состояния в «ничего не было».

## 11. Какие изменения распространяются на какие результаты

| Изменённый факт | Обязаны пересчитаться | Должны остаться прежними |
|---|---|---|
| Новый catalog price / offer BOM | новые pricing/proposal projections | agreed order, старый invoice candidate по неизменному milestone |
| Supplier ETA задержан | незакоммиченный план, обещания под риском, cash schedule, новая availability | историческая дата доставки, agreed contract deadline |
| Последний комплект зарезервирован | текущий ATP, feasibility другого заказа | каталог возможностей, уже выданная receipt первого резерва |
| Site access отозван | readiness/dispatch permission, schedule risk | agreed scope/price, прошлый монтажный протокол |
| Mapping точки исправлен с даты t | применимые новые вычисления и явно revised historical report | сырьевые записи и уже выпущенный report revision |
| Firmware release выпущен | eligible update plan для совместимого парка | installed firmware until confirmation, контрактная цена |
| Новая уязвимость затрагивает ревизию | support queue, risk, update plan, cost forecast | accepted support end date, незатронутые модели |
| SaaS suspended | feature entitlement по условиям, support explanation | hardware ownership, гарантийные даты и обещанный security support |
| RMA заменяет serial | текущая binding, stock, warranty disposition, service costs | point identity/history, customer agreed recurring units без expansion |
| Техническая приёмка подписана | trigger candidates по agreed policy, delivery completion | банковский cash received до реального поступления |
| Late telemetry прибыла | historical completeness/revised report | прошлая timely-delivery breach, сырая история инцидента |
| Изменено маркетинговое обещание | новая публичная проекция при разрешении | точность прибора, принятие старого заказа, физическая конфигурация |

## 12. Контрпримеры для будущих регрессионных тестов

Каждый случай — синтетический. В тесте нужны named facts, ожидаемое решение, authority boundary и минимум два выхода с propagation/non-propagation.

| ID | Сценарий | Ожидаемый результат |

## 13. Политики, измерения и гипотезы

| Класс | Что необходимо получить | Критерий пригодности |
|---|---|---|
| Выбранная политика | BOM, допустимые scope, acceptance procedure/tolerances, service calendar, SLA terms, support horizons, stock priority, returns, activation trigger | version, owner, effective dates, применимость к contract/units |
| Измеряемый engineering факт | совместимость, power/environment limits, buffer durability, measurement error, clock behavior, update recovery | конкретная конфигурация, методика, исходные результаты и область; vendor claim отдельно от собственного испытания |
| Измеряемый operating факт | lead time, install/commissioning hours, first-pass yield, revisit rate, support arrivals/handling time, RMA rates, telemetry quality | период/cohort, знаменатель, пропуски, distribution, исключения |
| Коммерческая гипотеза | платность обследования, приемлемость service windows, willingness to pay for premium replacement, tolerance for data gaps | интервью/пилотное поведение с разрешением; synthetic не evidence |
| Необходимая экспертная проверка | выбранная география, роли производителя/интегратора, установка, данные, warranty/security/retention obligations | scope-specific заключение; документ не выводит compliance=true |

До запуска pilot договора нужно закрыть: точный BOM; пригодные типы объектов; network/site prerequisites; ответственных за монтаж; actual acceptance thresholds; что означает paid point/site; activation и partial acceptance policy; численные SLA при обеспеченной capacity; support/security end dates; условия RMA/advance replacement; data/export/decommission policy; current authority operations. Остальные диапазоны можно держать предположениями для сравнения сценариев с явно условным результатом.

## 14. Предлагаемая первая реализация в DNA

Первый срез: один customer, site, accepted order, versioned kit, deployment и два кандидата на последний комплект/слот. Входы из маленьких fictional snapshots. Выходы: новое предложение, accepted work order, installation feasibility, commitment request, acceptance/billing candidate, subscription entitlement explanation, support runbook.

Первым реализовать OP-01/02/06/07/09/22/24/28 и таблицу propagation. Остальные разнести на supply, commissioning/data quality, support/lifecycle factories по реальным входам. Чистые функции сначала; DNA полезен там, где одни и те же факты поддерживают несколько результатов и нужны объяснение/impact. Исполнение reserve/activate/update/delete остаётся снаружи. Generic kernel не должен знать PowerTag, гарантийную формулу, state machine подписки или роль монтажника.
